4orm IQOperations auditAUD-002 · v1.030 September 2026Internal

What is running, what is broken, and what is being counted wrongly

A full audit of the 4orm IQ engine, its operations board and the registers behind it, taken on 30 September 2026. It records one defect that put a false picture of a registered dealer in front of a consumer, three faults that make a healthy system read as a broken one, and the controls that exist and are not being exercised.

Worst outcome

A registered dealer read as unconfirmed

Three separate faults combined to tell a consumer a registered Canadian firm could not be confirmed on any register, beside a foreign warning about a different company.

Worst exposure

Domain lookups are down

Every RDAP attempt in the window failed. The age of a domain is the single most predictive cheap signal this product has, and no run is getting it.

Most underrated

Nothing verifies the log on a schedule

The chain walk exists, is correct, and runs only when somebody asks for it by hand. The control is real and it is not being exercised.

Gate

The public site still says test build

The banner is accurate and it is the correct state. Clearing it needs SR-001 revised and the eight unsigned control documents signed.

01

The defect that matters most

A consumer checking a Canadian crypto exchange was shown a result headed we could not check enough to give you a reliable answer, carrying the sentence we could not confirm this business on a relevant register, with a foreign regulator's warning at the top of the record card and a single one-star review below it.

The company is registered. The Ontario Securities Commission publishes, on its own Crypto Businesses page, the crypto asset trading platforms that have received exemptive relief to offer crypto products in Ontario, with each platform's registration category and the date of its most recent decision.

Newton Crypto Ltd. · Restricted Dealer (Dealer) · March 12, 2025

Ontario Securities Commission, Registered Crypto Asset Trading Platforms. https://www.osc.ca/en/industry/registration-and-compliance/crypto-businesses · read 30 September 2026

Three independent faults produced that page. Each one is a defect on its own and each one is now closed or recorded.

The underlying error is one error, and it is worth naming plainly, because it is the error this company exists to prevent and we committed it: an absence in our own reading was published as a finding about somebody else.

03

Broken: the domain lookups

The health rule is deliberately narrow, and it is worth reading before the finding, because it is the reason this one is a real fault and not a display artefact.

function health(asked, answered){ if(!asked) return 'warn'; return answered>0 ? 'ok' : 'bad'; }

A lamp goes red only where the thing was tried and every attempt failed. Never on silence. The domain lamp is red, so RDAP was attempted on every applicable run in the window and returned nothing on all of them.

What that costs, specifically: the age of a domain is the cheapest strong signal in this product. A company claiming twelve years of operation on a domain registered six months ago is the finding that category 10 exists to produce, and category 10 cannot produce it without this lookup. Every run in the window has been running without it and no run said so on its face.

The fix, in two parts

First, restore the lookup. Second, and this is the part that outlives the outage: a run whose strongest check did not run must say so on the result. A degraded run that reads like a complete one is the same class of error as section 01, which is a gap in our reading reaching a consumer as a fact about a business.

04

Counted wrongly, and not counted at all

Every connector reads as refused on a healthy sweep

const connectorHealth = () => {
  ids.forEach(id => { const x = seen[id]; if(!x) return;
    tried += x.attempts || 0;
    ran   += (x.computed || 0) + (x.ok || 0); });
  if(!tried) return 'warn';
  return ran > 0 ? 'ok' : 'bad';
};

The reader adds computed to ok. The computed column is created by db/telemetry.sql, and that file has not been run against the production database. The column does not exist, the read yields nothing, ran stays at zero while tried climbs, and the rule returns bad on a sweep where nothing went wrong.

That is why every connector and all nine category tiles are red at once. A board that is entirely red is not reporting a system in trouble, it is reporting a board that cannot see. This is one psql run and no code change.

Spend prints zero across 108 checks

Same shape, different file. spend_run and spend_client come from db/spend.sql, which has also not been run. The rate variables KBYS_RATE_CLAUDE_IN_M and KBYS_RATE_CLAUDE_OUT_M are unset in the environment, so even with the tables present every row would price at nothing.

A cost control that reports zero is not a conservative cost control. It is an absent one, and the budget ceiling it is supposed to defend has never been tested against a real number.

05

The control that exists and is not exercised

The operations log is chained: every row carries the hash of the row before it and its own hash over that plus its content. Change any row after the fact and every hash after it stops matching. The walk that checks this is verifyChain, it is correct, and it has exactly one caller.

if (req.query.run === '1') { ... verifyChain(limit || null) }

Nothing schedules it. The gauge that reads Runs we can prove is not measuring the integrity of the log, it is measuring how much of the log somebody last walked by hand, which is why it reads 25 per cent. Three runs in four write a proof row and are never verified, because no verification has been run over them.

The number is not wrong. It is answering a different question from the one the label asks, which is the more dangerous of the two failures, because it looks like an answer.

The fix. A nightly walk through api/_scheduled.js behind KBYS_SCHEDULE_SECRET, an alert on any break, and a gauge whose label says what it measures. Competition Act s.74.01(1)(b) puts the onus of substantiating a performance claim on the party making it, and a chain head plus a scheduled verification is what discharging that looks like.

06

What shipped today, and why

Three changes went in against the section 01 defect and against the broader failure it is an instance of, which is that the engine only ever went looking for what was wrong.

The favourable side of the record, ranked by how hard it is to buy

RankWhat goes in itMay it move the result?
1 · Cannot be boughtA live registration, a licence in good standing, a regulator's own record, a filed financial statement, a court record showing a matter resolved, an exchange listing.No
2 · Expensive to fakeContinuity rather than content: the same legal name across three registers, on the register since 2018, a domain eight years old, a filing history without gaps.No
3 · Can be boughtStar ratings, review counts, testimonials, award badges, press releases.No

The third column is the whole design. Favourable evidence never changes the verdict. Register standing and adverse findings set the result and everything else is context beside it. The standing block is computed after the verdict is settled, it is never read back, and there is deliberately no code path from it to the verdict.

That is the defence against purchased reviews, and it is cheaper and more reliable than any detector: once a bought five-star page has nowhere to move the needle, buying one stops working. It also has no false positives, which a detector would, and a false positive here means calling a real customer a liar.

In 2024, of the 4.5 million detected fake reviews we removed from the platform, 90% were automatically detected by our fake review detection models.

Trustpilot Trust Report 2025. 4.5 million removals represent 7.4 per cent of all reviews submitted in 2024, against 6.1 per cent in 2023. https://corporate.trustpilot.com/trust/trust-report-2025 · read 30 September 2026

The final rule addresses reviews and testimonials that misrepresent that they are by someone who does not exist … The final rule prohibits certain reviews and testimonials written by company insiders that fail to clearly and conspicuously disclose the giver's material connection to the business.

Federal Trade Commission, final rule banning fake reviews and testimonials, 16 CFR Part 465, published 14 August 2024 and effective 60 days later. https://www.ftc.gov/news-events/news/press-releases/2024/08/federal-trade-commission-announces-final-rule-banning-fake-reviews-testimonials · read 30 September 2026

The time window

Businesses make mistakes and then fix them. A fault from four years ago that was put right should not sit over a company for the rest of its life.

BandAgeWhat it may do
currentInside 12 monthsDrives the result
older12 to 36 monthsShown and labelled. Drives nothing
archiveBeyond 36 monthsBehind one control the reader can open
undatedNo date on the recordNever a finding. Goes to what we could not confirm

Standing never ages. A register entry, a licence, a regulator action, a sanction and a court record describe what is true now until the issuing body changes them. A licence granted in 2019 is current. An enforcement order from 2021 that was never lifted is the present state of that party's record, not history. Ageing those out would be the single most dangerous thing this module could do, so they are exempt by class and can never fall into a band.

Why the window is arithmetic and not a judgement

“fresh” passages are consistently promoted, shifting the Top-10's mean publication year forward by up to 4.78 years … Although larger models attenuate the effect, none eliminate it.

Do Large Language Models Favor Recent Content? A Study on Recency Bias in LLM-Based Reranking, arXiv:2509.11353. Single passages moved as many as 95 ranks, and pairwise preferences between equally relevant passages flipped by up to 25 per cent after date injection. https://arxiv.org/html/2509.11353v1 · read 30 September 2026

So the model carries the date and does not weigh it. The band is computed in code from the date the record itself holds, where it is arithmetic and does not have that failure mode.

The change register

Every main change to this product and to the documents that govern it now has an entry, a reason, and a report behind it, at docs/change-register.json and in the control panel. An entry with no reason is rejected by the build. Nothing in it may carry an identifier anybody searched, a party a check was about, or a result a check returned, and that is enforced on the write path and checked again by the build.

08

Monitoring the nuance of the faults

The board today answers one question per lamp, which is whether the thing is working. That is the right question and it is not enough: every fault in this document was visible as a red lamp for some time before anybody could say what had actually failed, and two of them were not faults in the system at all.

ChangeWhat it answers
A reason on every failureSurface the recorded reason per failed attempt from the fault log, so a red lamp opens onto what the source actually returned rather than onto a count.
Worst offenders per lampWhich sources under this lamp are failing, ranked, so one dead connector stops presenting as nine dead categories.
Separate cannot see from is brokenA missing column, a missing environment variable and a refused request are three different states and the board paints all three the same colour. Sections 03 and 04 are two of each and they took a full audit to tell apart.
Alert on three conditions onlyA lamp that was green and is now bad. A chain break. A budget ceiling reached. Anything more and the alerts get muted, which is worse than not having them.

What could not be confirmed

This section is mandatory in a control document and it is not padding. Silence reads as verified.

ItemWhy not
The live RDAP failure reasonrdap.org returned 403 to this session. The lamp establishes that every attempt failed. It does not establish why, and no workaround was attempted.
The live values behind the board/api/stats is disallowed to automated fetching by our own robots file. The figures in section 02 are read from the board and the log, not fetched independently.
The full OSC decision for NewtonThe OSC order PDF at ord_20260311_newton-crypto.pdf returned 403. The registration entry quoted in section 01 is read from the OSC's own Crypto Businesses page, which is the controlling list.
Trustpilot's weighting formulaNot published. Their public statement is that the score is weighted to reflect that newer reviews tend to be more relevant than older ones, with no thresholds given. We did not model it and we do not rely on it.
How much evidence arrives undatedThe window only works where the source carries a date. Undated records are now named as gaps rather than counted, and the size of that population has not been measured on live traffic.
Terms 1.1Counsel has not reviewed it.
tools/protocheckCannot run in this environment: it loads a prototype file that is not in the repository. An environment gap, not a regression.
