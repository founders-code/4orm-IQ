02

Nine checks that could not run

The console moved from index.html to check.html when the landing page was built. Nine tools were still opening the old address, or a build tree that no longer exists on any machine. Each one either crashed on startup or passed against a page it was never written for, and a check that passes against the wrong page guards nothing.

The finding worth keeping. A previous pass reported that the gates had been put back in service. They had not: that pass matched one spelling of the old path and missed three others, including the form with a query string. The lesson is not about paths. It is that a repair to a test suite has to be proved by running the suite, and the suite had never been run.
03

Two rules that failed correct behaviour

Both were outside the gate, and both blamed the product for a copy edit.

RuleWhat was actually wrong
gatecheckAsserted the literal phrase our gap and not a finding. The line now reads a gap in our coverage, not a finding about the business, which says the same thing better. The rule now tests the two halves of the meaning: that the line claims the gap as ours, and that it disclaims a finding.
askagainGrepped too short while the refusal says still too broad. Its failure message read accepted and spent a run, which was never true: the guard fires and refuses before any spend. The rule now accepts any refusal that tells the reader the identifier is too vague.

A rule that fails correct behaviour is the same wound as a rule that cannot fail. One teaches people to ignore the suite; the other lets anything through. The repository already says so, in the header of tools/compliance.mjs: a rule that still passes with its subject removed is a green light with nothing behind it.

04

npm test could not have passed on a clean clone

tools/protocheck.mjs sat inside npm test and navigated to file:///home/claude/kbys/proto/flow.html, a prototype that is in no commit. Because the loop exits on the first failure, the gate stopped there for anybody who was not on the one machine that held that file. It is now out of npm test, and both proto tools carry a header saying they are out of service and why. Neither was deleted: deleting a check is how coverage disappears quietly, and neither was pointed at a substitute page, because a check that silently passes against the wrong target is the fault this audit is about.

One product defect, found by a repaired check

smoke33 is the phone contract, and the moment it could run it failed. The console header gained a way home and a label. Below 334 points that row is wider than the screen, so it wraps to the second line the nav is built to give it and the nav ends at 113 points instead of 73. The headline starts at 90 and was passing behind it. The clearance rule at 340 puts the headline at 114. Measured at 318, 322, 326, 330, 334, 340, 360, 375, 390, 414 and 430 points, with no sideways overflow at any of them.

The defect was ours, introduced the same week, and it was on the live site. It was found by a test that had been dead for long enough that nobody knew it was dead.

07

Two findings that outrank all of the above

The back office was being served to the public, with this register inside it

admin.html was deployed. It is a static asset, so Vercel sent all 731KB of it to anybody who asked, carrying the change register that tools/audit-embed.mjs writes into it at build time, including CR-0013's four still-open items, the ten control standards with their NO-GO states, and the release posture. The Clerk check on that page runs in the browser: it decides what is drawn, not what is sent. There is no middleware in this repository, and the page was confirmed served with no deployment protection in front of it.

CR-0013 excluded docs/ to stop this register being downloadable. It did not stop it being readable. A file excluded and a page carrying the same text deployed are the same disclosure with different plumbing, and the exclusion's own comment said the quiet part: admin.html embeds the register at build time, so it is not fetched at runtime.

Closed: admin.html is excluded, with the two ways to put it back written beside the line. tools/deploycheck.mjs is the gate, and it is section 04's answer as well as this one's. Filed as CR-0014, p0.

The product prints 175 registers in scope and the catalogue holds 135

api/_sr001.json carries total: 153 and an enabled array of 175 strings. That array is a name and alias allowlist and it also holds check descriptions, so its length is not a quantity of registers: 95 of the 175 match no register at all. POLICY.sources_enabled is that length, api/check.js:1123 sends it as registers_in_scope, and the report tells the reader the run covered 175 registers.

The caption is the smaller half. api/check.js counts a register out_of_scope when its display_name is absent from that array by exact string match. 55 of the 135 enabled registers are absent, so about two registers in five are counted out of scope on every run where they apply, and sources_out_of_scope is a hashed field in all three canonical versions in api/_ops.js.

So the tamper-evident chain is attesting a coverage figure that is wrong for two registers in five, against the promise written at api/check.js:869: coverage is COUNTED from the retrieval log rather than asserted. Do not cite the chain as coverage evidence until this is closed.

Not fixed, deliberately. Three numbers could be right and they mean different things: 135, every enabled register, which is what README.md says a page printing a register count must use; 96, the registers applicable to the run's vertical, which is the honest reading of the words in scope; 153, the manifest's own total. SR-001 is a signed workbook, so reinterpreting it is a governance decision and not a patch. tools/scopecheck.mjs fails the build on all four contradictions with the measured drift named, so the figure cannot be hashed into the chain unnoticed while the decision is open. Filed as CR-0016, p0.

08

What is still open

  1. complycheck is in the gate and red. It reports two content blockers: that the review process names a reviewer, a clock and the test but is a promise rather than a process, and that the privacy notice's route to it is only in the compliance statement, where nobody looking for privacy will find it. Both are copy and policy decisions, not code. Nothing in the deploy path runs npm test, so a red gate blocks no deploy. It blocks a claim, which is the point.
  2. protocheck and protoclip need a target in this repository or retirement.
  3. frames.mjs needs its own budget. At six minutes it does not fit the per-check ceiling, so it is recorded separately and could be missed.
  4. The suite is sequential and slow. A full record takes roughly twenty-five minutes, which is why it had never been taken.
